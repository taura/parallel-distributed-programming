Image stitching from scratch

(Baseline code not done yet, so this assignment is not finished. When done, I will re-submit from Jupyter as well as in UTOL.)

Problem

Image stitching is the process of combining multiple images/photos, with overlapping views of the scene, into a larger composed image with a wider view of the scene. The result is usually a segmented panorama image or one with full 360° view. Furthermore, rather than simply warping random image mosaics, appearance features on edges are aligned and “stitched” on the output panorama, ideally without noticeable visual seams.

The problem solved here is unlike the panorama feature commonly seen in smartphone camera apps:

  1. There’s no real-time stream of images, but to stitch from sparse samples with less overlaps of views.
  2. Lack of continuous stream also means image samples are unordered without associations in terms of overlaps.
  3. No IMU sensor to potentially aid with tracking camera orientation.

To ease the problem, I will begin with relaxing 2., requiring overlaps in input images. This will force the user to provide input images in a reasonable order.

Additional assumptions: * Input images are taken by the same camera with same settings (or at least similar). * We may ignore fine-grained improvements and optimization over the appearance of the image. Those extra credits will only be considered if time really permits.

How the algorithm/baseline code works

Since the task is rather high-level, I would omit the exact algorithms used for each step in the pipeline. Roughly speaking, for each image we have feature detection -> matching -> solve for transformation. Once all transformations are resolved, the scene can be built as some environment representation and/or rendered into a final panoramic image.

Where is parallelism

  • In general, most steps of the stitching pipeline operate independently on different images or pairs of images.
  • For feature detection on a single image, a thread-based mechanism may be too heavy, so I’m thinking about SIMD.
  • When having loads of input images, feature detection may be divided up into groups of images. A multithreaded approach could be beneficial.
  • The matching step only reads existing feature descriptors. The naive brute-force matching can be parallelized simply by splitting the comparison work by feature points. The better FLANN-based matching also have some potential that I have not yet digged into.
  • Solving a reasonable transformation between images, often a homography, can involve Direct Linear Transformormation (DLT), which requires solving systems of linear equations. This would call for some parallelized matrix operations.
  • RANSAC is commonly used to reject outlier matches. The iterations are independent and evaluations on data points can also be split.
  • Rendering to a panoramic view/canvas can be performed in parallel once the tranformations of each image is determined. (although I believe it is also feasible to render by sequential calls to drawing with OpenGL when available.)

I will prioritize parallelism on CPU, as the application will be more portable across types of devices, especially those on the edge. GPU-offloading may be considered when appropriate. As an extra bonus, it’s also worth exploring on-device processing of the pipeline on GPU with CUDA.
